# Redis LLM Bridge — протокол и эксплуатация

Версия протокола: 1. Статус: действующий.

Транспорт локальной LLM через Redis Streams: приложение (SDP, ПРОМ-кластер
`10.110.10.38`) ↔ воркер (Jupyter DataLab). На SDP нет ни прямого доступа к
GigaChat API, ни к локальным inference-серверам (sglang/vLLM) — оба доступны
только из окружения DataLab. Redis ПРОМа (`10.110.10.38:7474`) достижим с
обеих площадок, поэтому он служит единственным общим каналом: заявка на
LLM-запрос сериализуется в приложении, уходит через Redis Stream, исполняется
воркером на DataLab против нужного бэкенда и возвращается тем же путём.

Конвенции этого биндинга (конверты, consumer group, heartbeat, XAUTOCLAIM) —
осознанная обкатка для будущей миграции шины внешнего ИИ-агента с БД на Redis
Streams (см. `docs/integrations/agent-bus-redis-binding.md`). Затрагивается
только путь локальной LLM (`orchestrator.run` при `agent_mode` `off`/`adaptive`,
text actions) — шина `chat_agent_messages_bus` этим документом не описывается.

## 1. Роли и владение

Приложение владеет контрактом: форматом конвертов, именами ключей, версией
протокола и трансляцией форматов LLM-провайдеров. Воркер — тупой исполнитель:
берёт заявку, делает HTTP POST на URL цели с её токеном, возвращает сырой
ответ и тайминги, никакой трансляции форматов не делает. Обе стороны живут в
одном репозитории, поэтому обновляются согласованно:

- приложение — `app/domains/chat/services/redis_bridge_adapter.py`
  (клиент `RedisBridgeClient`) и `app/domains/chat/settings.py`
  (`parse_route`, `RedisBridgeSettings`);
- воркер — `scripts/llm_redis_worker.ipynb`, запускается вручную на
  DataLab.

Раздельного версионирования протокола на два репозитория нет: правка формата
конверта требует правки обеих сторон в одном PR.

## 2. Сущности и ключи

Все ключи — под общим префиксом `key_prefix` (настройка
`CHAT__REDIS_BRIDGE__KEY_PREFIX`, дефолт `llm:bridge:`).

| Ключ | Тип | Назначение |
|---|---|---|
| `{prefix}requests` | Stream | Заявки на LLM-запрос. Consumer group `llm-workers`. `XADD` с `MAXLEN ~ 1000` (аппроксимация, без блокировки на трим) — старые необработанные заявки вытесняются, если очередь переполняется дольше, чем воркер успевает разбирать |
| `{prefix}resp:{id}` | Stream | Кусочки ответа на конкретную заявку `{id}` (uuid4). Сегодня пишется один терминальный кусок (`final`/`error`); `TTL 300` сек через `EXPIRE` сразу после `XADD`, чтобы ответы не копились в Redis бессрочно |
| `{prefix}worker:alive` | String (JSON) | Heartbeat воркера. `SET ... EX 45`, обновляется каждые 15 сек из отдельной asyncio-задачи, параллельно обработке заявок. Помимо статуса (`worker_id`, `targets`, счётчики) несёт `target_health` — карту `{цель: bool}` по результату `GET /models` каждой цели в heartbeat-такте (здоровье = статус < 500). Пользовательский путь (`create`) на `target_health` НЕ смотрит; его читает только health probe приложения — breaker закрывается, лишь когда жив и воркер, и LLM-бэкенд за ним |

Имя consumer group — `llm-workers`, задаётся константой
`CONSUMER_GROUP` в `redis_bridge_adapter.py` (там же — для справки и тестов;
саму группу на стриме создаёт воркер через `XGROUP CREATE ... MKSTREAM`).

## 3. Конверт заявки

Поля `{prefix}requests` (все значения — строки, как того требует Redis Streams):

| Поле | Тип | Семантика |
|---|---|---|
| `v` | str | Версия конверта, сейчас `"1"` |
| `id` | str (uuid4) | Идентификатор заявки; также ключ ответа `{prefix}resp:{id}` |
| `target` | str | Цель воркера: `gigachat` \| `openai`. Совпадает с проводным форматом тела — отдельной карты «цель → формат» нет |
| `path` | str | Путь на бэкенде цели; сейчас всегда `/chat/completions` |
| `body` | str (JSON) | Тело запроса в проводном формате цели — трансляцию (OpenAI ↔ GigaChat native) делает приложение до отправки, воркер тело не трогает. `stream` и `tool_choice` из вызова отбрасываются клиентом: стриминга в v1 нет, а `tool_choice` не поддерживает GigaChat (как и в `gigachat_adapter`) |
| `deadline_ts` | str (unix float) | Дедлайн ожидания, считается на часах приложения (`time.time() + timeout`). Воркер сравнивает со своими часами — NTP-рассинхрон предполагается небольшим, а сам дедлайн достаточно грубый (десятки-сотни секунд), чтобы это было некритично |

`target` — одновременно и имя цели в карте воркера `TARGETS`, и проводной
формат тела (`wire_format`): какой реальный сервер стоит за целью `openai`
(sglang, vLLM, ...), знает только воркер, приложению это не нужно.

## 4. Конверт ответа

Поля кусочка в `{prefix}resp:{id}`:

| Поле | Тип | Семантика |
|---|---|---|
| `v` | str | Версия конверта, `"1"` |
| `seq` | str (int, с 0) | Порядковый номер кусочка. В v1 всегда `"0"` — стриминга нет |
| `kind` | str | `chunk` \| `final` \| `error` |
| `status_code` | str (int) | Для `final` — код ответа бэкенда (2xx); для `error` — код ошибки |
| `body` | str (JSON) | Только для `final` — сырое тело ответа бэкенда как есть, без трансляции (трансляцию в `ChatCompletion` делает клиент в приложении) |
| `message` | str | Только для `error` — текст ошибки для логов, пользователю не показывается напрямую |
| `received_ts` | str (unix float) | Момент, когда воркер принял заявку в обработку (записывается сразу при чтении entry) |
| `started_ts` | str (unix float) | Момент начала HTTP-вызова к бэкенду (после ожидания rate limit) |
| `finished_ts` | str (unix float) | Момент получения ответа/ошибки от бэкенда |

`kind=chunk` зарезервирован под v2 (по-кусочный стриминг ответа) и сейчас
воркером не пишется. Тайминги пишутся уже в v1, хотя сами LLM-метрики
(таблица, батчер, страница админки) — отдельная работа вне скоупа моста;
конверт готовится заранее, чтобы не менять протокол ради их появления.

## 5. Жизненный цикл заявки

1. **Heartbeat-чек.** Клиент (`_ensure_worker_available`) читает
   `{prefix}worker:alive`; ключа нет, Redis недоступен или `target` не входит
   в список `targets` из JSON — мгновенный отказ ещё до `XADD` (см. §6).
2. **`XADD {prefix}requests`** с конвертом заявки (§3), `MAXLEN ~ 1000`.
3. **`XREADGROUP`** (воркер, consumer group `llm-workers`, `BLOCK 5000 COUNT 1`)
   — воркер вычитывает заявку по своему consumer-имени (`hostname:pid`).
4. **Rate limit по цели** — воркер выдерживает `rate_limit_sec` между
   вызовами одной и той же цели (GigaChat: 5 сек; openai-цель: без лимита).
5. **`POST`** на URL цели с её токеном.
6. **Ретраи** — 429/5xx/сетевые ошибки повторяются с паузами 5→10→20 сек, не
   более `MAX_ATTEMPTS=3` попыток и не позже дедлайна заявки; остальные 4xx
   (включая 408) воркер не ретраит, а возвращает `error`-конвертом — решение
   о повторе принимает приложение своей retry-политикой (`retry.py` ретраит
   408 всегда).
7. **`XADD {prefix}resp:{id}`** терминального кусочка (`final`/`error`) +
   **`EXPIRE {prefix}resp:{id} 300`**.
8. **`XACK`** заявки в consumer group — только после того, как ответ записан
   (в `finally`, чтобы заявка не осталась висеть в PEL при внутренней ошибке
   обработки).

В начале каждой итерации consumer-цикла — **`XAUTOCLAIM`** (min-idle 10 мин,
до 10 заявок за раз): если воркер упал между `XREADGROUP` и `XACK`,
следующий запуск воркера подбирает зависшую в PEL заявку и доделывает её.
Порог 10 мин выбран выше worst-case живой обработки (~6 мин: HTTP-таймаут
120 сек × 3 попытки + паузы ретраев + rate limit) — иначе второй воркер
украл бы заявку, которую первый ещё обрабатывает, и бэкенд получил бы
дубль-вызов. Заявки, чей `deadline_ts` уже истёк на момент подбора,
пропускаются без записи ответа — клиент к этому моменту уже получил
`BridgeDeadlineError` самостоятельно (см. §6), повторный ответ ему не нужен.

Клиент, со своей стороны, после `XADD` заявки поллит `XRANGE {prefix}resp:{id}`
каждые 0.3 сек до появления терминального кусочка или своего дедлайна.

## 6. Ошибки и их отображение

Ошибки моста транслируются в иерархию исключений `openai.*` — иначе
существующие слои retry (`retry.py`), circuit breaker и fallback (`llm_call.py`)
их не увидят и не смогут среагировать так же, как на прямой HTTP-сбой.

| Ситуация | Исключение | Реакция системы (существующая) |
|---|---|---|
| Heartbeat нет / цель не в списке `targets` | `APIConnectionError` | connect-класс retry (до 2 попыток), circuit breaker, fallback, error-блок |
| Redis недоступен (сбой команды `GET`/`XADD`/`XRANGE`) | `APIConnectionError` | то же |
| Дедлайн ожидания истёк | `BridgeDeadlineError` (подкласс `APITimeoutError`) | БЕЗ retry (дедлайн = полный `CHAT__REQUEST_TIMEOUT`; повтор клал бы в stream дубль-заявку, воркер исполнял бы её против LLM), но circuit breaker + fallback срабатывают как обычно |
| Воркер вернул `error` со статусом 5xx / 429 / 408 | `APIStatusError(код)` | ретраится по обычной retry-политике |
| Воркер вернул `error` со статусом 4xx (кроме 408/429) | `APIStatusError(код)` | пробрасывается без ретраев и без fallback |
| Тело `final`-конверта нечитаемо / не проходит схему `ChatCompletion` | `APIStatusError(502)` | ретраится по on_5xx, circuit breaker, fallback; в тексте ошибки — причина разбора, а не «сбой Redis» |

Пользователь во всех случаях видит штатный error-блок (код `llm_unavailable`),
новых текстов ошибок мост не добавляет — с точки зрения оркестратора сбой
через Redis неотличим от сбоя прямого HTTP-вызова. Типичный сценарий отказа:
«GigaChat лёг → едем на openai-цель того же воркера» — primary
(`redis-bridge,gigachat`) исчерпывает ретраи или его цель пропадает из
heartbeat, circuit breaker размыкается, оркестратор переключается на
fallback-клиент (`redis-bridge,openai`), который может указывать на тот же
воркер, но другую цель.

## 7. Долговечность и часы

Redis ПРОМа используется как кэш-слой без AOF — это осознанное решение:
потеря заявок при падении Redis допустима. Заявка эфемерна (живёт секунды —
десятки секунд ожидания ответа LLM), при потере Redis приложение просто
ответит пользователю штатной ошибкой недоступности LLM, как и при любом
другом транспортном сбое. Это отличается от будущей миграции шины внешнего
агента, где вопрос долговечности решается отдельно (вопросы там могут висеть
в очереди агента часами и требуют более сильных гарантий).

По часам — `deadline_ts` считается на часах приложения и сравнивается
воркером на своих часах. Небольшой NTP-рассинхрон между SDP и DataLab
допускается: сам дедлайн достаточно грубый (обычно 60–180 сек,
`CHAT__REQUEST_TIMEOUT`), чтобы разница в единицы секунд не имела значения.

## 8. Запуск воркера на DataLab

**Требование к Redis: версия ≥ 7.0.** Воркер использует `XAUTOCLAIM` с
3-элементным ответом (`next_cursor, claimed, deleted_ids`) — этот формат
появился в Redis 7.0; на более старых версиях `XAUTOCLAIM` возвращает
2-элементный кортеж, и разбор ответа в воркере упадёт. ПРОМ и DEV используют
Redis `7.0.15` (см. `docs/guides/redis-dev-wsl-guide.md` для DEV-окружения на
WSL) — требование выполнено на обеих площадках.

Запуск:

1. Открыть `scripts/llm_redis_worker.ipynb` в Jupyter DataLab.
2. Проверить переменные окружения перед запуском:
   - `GIGACHAT_API_URL`, `JPY_API_TOKEN` — для цели `gigachat` (обычно уже
     инжектированы окружением DataLab);
   - `OPENAI_API_URL` (и `OPENAI_API_KEY`, если бэкенд требует авторизацию) —
     для цели `openai`; локальный sglang/vLLM без авторизации — легальная
     цель, токен опционален;
   - `BRIDGE_REDIS_HOST` / `BRIDGE_REDIS_PORT` / `BRIDGE_REDIS_PASSWORD` —
     только если отличаются от ПРОМ-дефолтов (`10.110.10.38:7474`, без
     пароля), заданных константами в ноутбуке.
3. **Run All.** В выводе конфигурационной ячейки появится строка вида
   `Воркер <hostname>:<pid>; доступные цели: [...]` — цель попадает в список,
   если у неё задан `url` (token опционален). Пустой список целей
   означает, что воркер поднялся, но ни одна цель не сконфигурирована —
   приложение увидит heartbeat, но любой запрос упадёт с «цель недоступна».
4. **Остановка** — Kernel → Interrupt на ячейке запуска. Воркер гасит обе
   задачи (heartbeat и consumer), удаляет ключ `worker:alive` и закрывает
   соединение с Redis — приложение видит недоступность моста сразу (heartbeat
   не нужно ждать до истечения TTL). Порядок важен: heartbeat снимается
   последним, иначе живая heartbeat-задача пересоздала бы ключ после `DEL` и
   приложение видело бы «зомби»-воркера, который ничего не потребляет.

**DEV-запуск (локально, без DataLab).** Ноутбук содержит отдельную ячейку
«DEV: переменные окружения» и markdown-чеклист быстрой проверки: локальный
воркер + локальный Redis (`127.0.0.1:6379`) + облачный OpenAI-совместимый
бэкенд, при `CHAT__PROFILE=redis-bridge,openai` в `.env`. Переменные
(`OPENAI_API_URL`, `OPENAI_API_KEY`, `BRIDGE_REDIS_HOST`/`PORT`) достаточно
задать через `$env:` **до** старта Jupyter из того же шелла; если kernel
поднят иначе (например, из VS Code), переменные не наследуются — тогда
заполняется DEV-ячейка ноутбука.

## 9. Smoke-чеклист

Проверка после запуска/перезапуска воркера или деплоя приложения (на DEV те же
команды без `-h`/`-p` — Redis локальный, см. `docs/guides/redis-dev-wsl-guide.md`):

- `redis-cli -h 10.110.10.38 -p 7474 GET llm:bridge:worker:alive` — должен
  вернуться JSON с непустым `targets`; отсутствие ключа означает, что воркер
  не запущен или heartbeat уже истёк (TTL 45 сек).
- `redis-cli -h 10.110.10.38 -p 7474 XLEN llm:bridge:requests` — глубина
  очереди заявок; устойчиво растущее значение говорит, что воркер не
  вычитывает stream (упал, завис на рейт-лимите, сетевая проблема до цели).
- Отправить сообщение в чат при `CHAT__PROFILE=redis-bridge,gigachat` —
  должен прийти обычный ответ ассистента (без видимой разницы с прямым
  HTTP-транспортом).
- Остановить воркер (Kernel → Interrupt) → отправить сообщение в чат →
  ожидается мгновенная штатная ошибка (`APIConnectionError` из-за
  отсутствующего heartbeat), а не зависание до таймаута.
- Запустить воркер заново → следующее сообщение в чат должно отработать без
  рестарта приложения — клиент моста не кэширует состояние «воркер мёртв»
  между запросами, каждый вызов заново проверяет heartbeat.

## 10. Версионирование

Каждый конверт (и заявки, и ответа) несёт поле `v`. Несовместимое изменение
формата — инкремент версии; поскольку воркер и приложение живут в одном
репозитории, обе стороны обновляются в одном PR, отдельного механизма
согласования версий между процессами не требуется. Пример совместимого
расширения без слома — уже заложенный в v1 `kind=chunk` для будущего
по-кусочного стриминга ответа (v2): читающая сторона просто не встретит
`chunk` в текущей версии протокола.
