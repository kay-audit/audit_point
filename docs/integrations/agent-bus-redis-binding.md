# Шина внешнего агента на Redis Streams — проект контракта

Статус: **ПРОЕКТ**. Вступает в силу после решения о миграции транспорта шины
(работа А из `docs/reports/agent-bus-transport-and-protocol.md`, §2). До этого
момента действующий транспорт — таблица БД, её контракт в этом документе не
описан.

Биндинг обкатан на соседней задаче — мосте локальной LLM через Redis Streams
(`docs/integrations/redis-llm-bridge.md`): те же конверты, consumer group,
heartbeat и `XAUTOCLAIM`. Этот документ адресован внешней команде ИИ-агента
БЗ ОАРБ — стороне, которая читает и пишет в шину со своей стороны.

Далее по тексту **AW** — сторона-заказчик вопросов (Audit Workstation),
**агент** — сторона БЗ ОАРБ, отвечающая на них.

## 1. Принципы

- **Contract-first.** Формат конвертов, имена ключей и словари значений
  фиксируются этим документом, а не выводятся из кода одной из сторон.
  Правки — по договорённости обеих сторон, а не молчаливым изменением
  реализации.
- **Версия в каждом сообщении.** Конверт вопроса, конверт ответа и heartbeat
  несут поле `v`. Несовместимое расширение формата — инкремент версии, а не
  добавление поля без предупреждения. Сторона, встретившая незнакомую версию,
  вправе отказаться от обработки, а не гадать о семантике новых полей.
- **Иммутабельные записи стримов — дельты вместо UPDATE.** В прежнем
  контракте ответ был одной строкой таблицы, которую агент обновлял по мере
  готовности (рост `metadata.reasoning`, смена `status`). Redis Streams не
  умеет обновлять запись — вместо этого агент пишет последовательность
  отдельных конвертов-дельт, а читающая сторона накапливает их сама.
- **Heartbeat вместо неявного «жив, раз пишет».** Прежний контракт не имел
  явного признака «агент вообще запущен» — AW судил о живости агента только
  по движению записей конкретного ответа. Явный heartbeat-ключ с коротким TTL
  даёт мгновенный и однозначный сигнал ещё до того, как AW отправит вопрос.
- **Явные словари значений с владельцем.** Значения `kind` (тип конверта
  ответа) перечислены в этом документе целиком (§2.4, §6); словарь не
  является внешней структурой (CHECK-констрейнтом чужой таблицы), которую
  можно поменять без уведомления другой стороны. `status_code` — HTTP-подобный
  числовой код результата; его словарь фиксируется при согласовании контракта
  (открытый вопрос, §8).
- **Таймауты двусторонне известны.** Оба таймаута AW (взятие в работу,
  ожидание ответа) и правило поведения агента при их истечении зафиксированы
  в §5 — сторона-агент не должна выяснять их эмпирически.
- **Недвусмысленные метки времени.** Все временные поля — unix-эпоха (число
  секунд с плавающей точкой), а не серверный тип с часовым поясом. Это снимает
  класс ошибок «наивная метка времени с одной из сторон сдвигает все отсечки
  по возрасту».
- **Уникальность `id` вопроса — ответственность генерирующей стороны, не
  гарантия транспорта.** Redis Stream сам присваивает уникальный монотонный
  ID только записям *внутри* потока — но `id` вопроса, которым адресуется
  поток ответа `{prefix}answer:{id}`, генерирует AW (`uuid4`), и Redis эту
  генерацию никак не проверяет: `XADD` в уже существующий ключ молча
  дописывает запись, а не отказывает, как отказал бы PK в БД. Аналога
  PK-отказа у Redis нет; уникальность целиком опирается на коллизионную
  стойкость `uuid4` (см. MUST-таблицу).
- **Направление задаётся ключом, не полем.** Вопрос всегда пишется AW в поток
  вопросов, ответ — агентом в поток, привязанный к id этого вопроса. Отдельное
  поле «роль» (user/assistant/system), которое можно перепутать при записи, не
  нужно.

## 2. Схема потока

### 2.1 Ключи

| Ключ | Тип | Кто пишет | Кто читает | Назначение |
|---|---|---|---|---|
| `{prefix}questions` | Stream | AW | Агент (consumer group) | Единый поток вопросов от AW к агенту |
| `{prefix}answer:{id}` | Stream | Агент | AW | Дельты и финал ответа на конкретный вопрос с идентификатором `{id}` |
| `{prefix}agent:alive` | String (JSON) | Агент | AW | Heartbeat: агент запущен, список поддерживаемых опциональных возможностей |

`{prefix}` — общий префикс ключей шины, конкретное значение фиксируется
конфигурацией AW и сообщается агенту отдельно (аналогично `key_prefix`
LLM-моста). Имя consumer group на `{prefix}questions` задаётся AW и также
сообщается агенту отдельно — в этом документе не фиксируется.

### 2.2 Диаграмма потока

```mermaid
sequenceDiagram
    participant AW as AW
    participant R as Redis
    participant Ag as Агент

    par Heartbeat агента (независимо от вопросов)
        loop каждые N сек
            Ag->>R: SET agent:alive (JSON, capabilities) EX 3N
        end
    end

    AW->>R: GET agent:alive
    alt ключа нет или Redis недоступен
        R-->>AW: (пусто) / ошибка
        AW->>AW: мгновенный отказ, вопрос не создаётся
    else агент жив
        R-->>AW: JSON heartbeat
        AW->>R: XADD questions (конверт вопроса, v, id, deadline_ts, ...)
        Ag->>R: XREADGROUP questions (consumer group)
        R-->>Ag: конверт вопроса

        alt deadline_ts вопроса уже истёк на момент взятия
            Ag->>Ag: вопрос пропускается, ответ не пишется
        else вопрос актуален
            loop дельты рассуждений (опционально)
                Ag->>R: XADD answer:{id} (kind=chunk, seq=N)
            end
            Ag->>R: XADD answer:{id} (kind=final или kind=error)
            Ag->>R: XACK questions {id}

            loop поллинг AW до терминального kind или своего таймаута
                AW->>R: XRANGE answer:{id}
                R-->>AW: накопленные конверты
            end
        end
    end

    note over Ag,R: При падении агента между XREADGROUP и XACK — вопрос виден в PEL;\nследующий запуск агента подбирает его через XAUTOCLAIM
```

### 2.3 Конверт вопроса (`{prefix}questions`)

| Поле | Тип | Семантика |
|---|---|---|
| `v` | str | Версия конверта |
| `id` | str (uuid4) | Идентификатор вопроса; также имя ключа ответа `{prefix}answer:{id}` |
| `chat_id` | str | Идентификатор треда на стороне AW |
| `user_id` | str | Идентификатор пользователя AW, задавшего вопрос |
| `content` | str | Текст вопроса |
| `deadline_ts` | str (unix float) | Дедлайн ожидания ответа, считается на часах AW |

### 2.4 Конверт ответа (`{prefix}answer:{id}`)

| Поле | Тип | Когда обязательно | Семантика |
|---|---|---|---|
| `v` | str | всегда | Версия конверта |
| `seq` | str (int, с 0) | всегда | Порядковый номер конверта в этом stream, строго монотонный |
| `kind` | str | всегда | `chunk` \| `final` \| `error` |
| `reasoning_delta` | str | только `chunk` | Очередной кусок текста рассуждений; AW склеивает по возрастанию `seq` |
| `content` | str | только `final` | Финальный текст ответа |
| `buttons` | str (JSON) | опционально, только `final` | Список кнопок (см. §4) |
| `status_code` | str (int) | `final` / `error` | Код результата |
| `message` | str | только `error` | Текст ошибки для лога агента и AW, пользователю не показывается напрямую |

### 2.5 Heartbeat (`{prefix}agent:alive`)

JSON-объект с полем `capabilities` — списком опциональных возможностей,
которые агент фактически поддерживает (например, пишет ли дельты рассуждений,
умеет ли отдавать кнопки). Живость ключа определяется исключительно его
наличием (TTL, см. §5) — содержимое информативное, не обязывающее.

## 3. Обязательно (MUST)

| Требование | Зачем | Что случится при нарушении |
|---|---|---|
| Версия конверта `v` — в вопросе, каждой дельте ответа и heartbeat | Позволяет распознать несовместимое расширение протокола до разбора остальных полей | Сторона получает конверт с неизвестной семантикой полей и не может понять, безопасно ли его игнорировать |
| `id` вопроса — `uuid4`, генерируется AW при создании вопроса | Redis не проверяет уникальность ключа при `XADD` и не отвергает коллизию — гарантия целиком на генерирующей стороне | Совпадение `id` у двух разных вопросов — `XADD` в чужой `{prefix}answer:{id}` молча допишет туда конверт, ответы двух разных вопросов перепутаются в одном потоке |
| Ответ пишется в поток `{prefix}answer:{id}`, привязанный к id вопроса — НЕ отдельной записью с полем-указателем на вопрос | Адресация уже задана ключом, отдельное поле избыточно и может разойтись с реальным вопросом | AW не найдёт ответ по ожидаемому ключу и закроет вопрос по таймауту, хотя агент уже отвечает |
| Ретрай ответа — дозапись нового конверта в тот же `{prefix}answer:{id}`, «последний терминальный конверт побеждает» | Явное правило вместо создания второго вопроса или второго адреса ответа на тот же вопрос | Без явного правила AW может показать пользователю первый (возможно, ошибочный) терминальный конверт и никогда не увидеть исправленный |
| Терминальный конверт (`kind=final` либо `kind=error`) — ровно один на вопрос | AW прекращает поллинг по первому терминальному конверту | Второй терминальный конверт после первого никогда не будет прочитан — ответ теряется |
| `XACK` вопроса в consumer group — только после того, как терминальный конверт ответа записан | При падении агента между чтением вопроса и записью ответа вопрос должен пережить рестарт и быть подобран повторно через `XAUTOCLAIM` | Ранний `XACK` без ответа — вопрос теряется безвозвратно, `XAUTOCLAIM` его больше не увидит |
| Heartbeat-ключ обновляется не реже раза в N сек, TTL ключа = 3N | Отсутствие ключа — единственный сигнал AW «агент недоступен», по которому AW отказывает вопрос ещё до `XADD` | Слишком короткий TTL относительно интервала обновления даёт ложные «агент недоступен» на обычных паузах сети или GC |
| Ошибка — отдельным конвертом `kind=error` со `status_code`, а не тишиной (отсутствием ответа) | AW должен различать «агент ещё работает» и «агент отказался отвечать» по явному сигналу, а не по отсутствию событий | Тишина неотличима от зависшего агента — пользователь ждёт полный таймаут ради ошибки, которую агент уже знал сразу |
| Просроченный вопрос (`deadline_ts` истёк на момент взятия в работу, включая подбор через `XAUTOCLAIM`) не исполняется, ответ не пишется | AW уже закрыл такой вопрос как отказ и показал пользователю ошибку по истечении своего таймаута — ответ на него станет «ответом-сиротой», который некому показать | Агент тратит вычислительные ресурсы на вопрос, ответ на который гарантированно не дойдёт до пользователя |

## 4. Опционально (MAY)

| Возможность | Семантика | Примечание |
|---|---|---|
| Дельты рассуждений (`kind=chunk`, монотонный `seq`) | Агент может не стримить рассуждения вовсе — тогда ответ состоит из одного `kind=final` | Заменяет поле `metadata.reasoning` прежнего контракта |
| Кнопки (`buttons`, только в финальном конверте) | `action_id` каждой кнопки — имя зарегистрированного на стороне AW действия | Набор допустимых `action_id` и их параметров — часть контракта, версионируется вместе с ним; неизвестный AW `action_id` не исполняется |
| Media (изображения, файлы) | В v1 **не поддерживается** ни в каком виде | Явный запрет, а не пропуск в описании — путь доставки файлов от агента пользователю сегодня технически не работает; добавлять поле в контракт раньше починки этого пути не имеет смысла |
| Перечень возможностей в heartbeat (`capabilities`) | Агент заявляет, какие опциональные фичи он фактически использует | Информативное поле: AW ориентируется на факт появления соответствующих `kind` в ответе, а не только на заявленный список |

## 5. Тайминги

Оба таймаута AW — **idle**: отсчёт ведётся не от создания вопроса, а от
последнего признака жизни агента (колонка 3). Текущие значения на стороне AW —
30 мин на взятие в работу (`CHAT__AGENT_CHANNEL__CLAIM_TIMEOUT_SEC=1800`) и
30 мин на ответ (`CHAT__AGENT_CHANNEL__ANSWER_TIMEOUT_SEC=1800`); они же
действуют в текущем БД-транспорте и переносятся в Redis-биндинг без изменений.

| Таймаут | Владелец | Признак жизни, сбрасывающий отсчёт | Действие AW по истечении | Действие агента при просрочке |
|---|---|---|---|---|
| Взятие вопроса в работу (30 мин idle) | AW | Вопрос перешёл под конкретного consumer'а (виден в `XPENDING`) | AW закрывает вопрос как отказ, освобождает слот лимита параллельных запросов, показывает пользователю ошибку | Агент, обнаруживший вопрос с истёкшим `deadline_ts` — при обычном чтении или при подборе через `XAUTOCLAIM` — не берёт его в обработку (см. MUST-таблицу) |
| Ожидание ответа (10 мин idle) | AW | Рост `seq` в `{prefix}answer:{id}` — новый конверт с более поздним stream ID, чем на предыдущем опросе | AW прекращает поллинг, закрывает вопрос как отказ, показывает пользователю ошибку | Если агент уже начал писать дельты до истечения таймаута, технически он может продолжать — но AW эти записи больше не прочитает, сигнал живости для пользователя потерян безвозвратно |
| Heartbeat (агент в принципе доступен) | Агент | Периодический `SET {prefix}agent:alive ... EX 3N` | AW проверяет ключ ещё до `XADD` вопроса; отсутствие ключа — мгновенный отказ без создания вопроса | Поддержание ключа — обязанность агента, отдельного таймаута со стороны AW здесь нет |

## 6. Словари и владение

Прежний (БД) контракт хранил статус вопроса и ответа в колонке `status` с
CHECK-констрейнтом, которым владел агент, а AW писал в неё best-effort,
глотая нарушения. В Redis-биндинге статус — это поле `kind` конверта ответа
(§2.4), значения которого перечислены целиком в этом документе, а не во
внешней структуре, которую можно сменить без уведомления. Расширение словаря
значений `kind` — только через инкремент версии протокола `v` (§1), никогда
молча.

Отдельного поля «роль» (`user`/`assistant`/`system`) не требуется: направление
задаётся тем, в какой поток идёт запись — вопрос всегда в `{prefix}questions`,
ответ всегда в `{prefix}answer:{id}` конкретного вопроса.

Позиция и объём очереди: раньше это был `COUNT(*)` по всей таблице с фильтром
по статусу и возрасту — сканирование растущей таблицы, дорожающее со временем,
и без фильтра по пользователю (число «вопросов передо мной» включало чужие
вопросы). В Streams аналог — `XLEN {prefix}questions` (общая глубина очереди)
и `XPENDING` (вопросы, уже взятые агентом, но не подтверждённые). Оговорка:
это по-прежнему общая для всех пользователей метрика — сама по себе смена
транспорта не даёт точного «N человек передо мной», если агент не введёт
отдельное шардирование по пользователю.

Ретеншн вопросов решается ограничением длины `{prefix}questions` (`MAXLEN`
при записи) — старые обработанные вопросы не обязаны храниться бессрочно.
Ретеншн потоков ответов `{prefix}answer:{id}` этим документом не закрыт —
см. открытый вопрос в §8.

## 7. Отличия от LLM-моста

| Аспект | LLM-мост (`redis-llm-bridge.md`) | Шина внешнего агента (этот документ) |
|---|---|---|
| Кратность ответа | 1:1 — один терминальный конверт сразу | Может быть серия дельт (`kind=chunk`) перед терминальным конвертом |
| Долговечность | Redis — кэш-слой без AOF, потеря заявки допустима: заявка живёт секунды | Вопрос может висеть в очереди агента часами — допустимость потери требует отдельного решения (§8) |
| Ретеншн ответа | `EXPIRE 300` сек сразу после записи терминального конверта | Не зафиксирован в этом проекте контракта (§8); ретеншн вопросов решён через `MAXLEN` |
| Кто владеет обеими сторонами конверта | Приложение и воркер — один репозиторий, один PR на изменение формата | AW и внешняя команда агента — разные репозитории; версия протокола `v` — единственный механизм согласования |
| Heartbeat | Проверяется перед каждой заявкой, отсутствие — мгновенный отказ | То же самое, плюс список возможностей агента (`capabilities`) |

## 8. Открытые вопросы

1. Готова ли команда агента писать/читать Redis, и есть ли у неё сетевой
   доступ к инстансу Redis AW — или потребуется отдельный инстанс/реплика?
2. Допустима ли потеря неотвеченных вопросов при падении Redis? В отличие от
   LLM-моста, где заявка живёт секунды, вопрос к внешнему агенту может висеть
   в очереди часами — цена потери выше.
3. Нужна ли история переписки с агентом в шине после того, как ответ получен,
   или шина — чистый транспорт, а история хранится на стороне AW? От ответа
   зависит ретеншн потоков `{prefix}answer:{id}` (не решён этим документом —
   ретеншн `{prefix}questions` через `MAXLEN` не покрывает ответы).
4. Переезд разовый (согласованное окно, обе стороны переключаются
   одновременно) или нужен период dual-write, когда живы оба транспорта —
   таблица БД и Redis Streams?
5. Кто со стороны команды БЗ ОАРБ владеет этим контрактом и подписывает
   последующие изменения версии протокола?
